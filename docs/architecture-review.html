proveit architecture review

Deepening candidates, deletion test, and a behavior-preservation gate

Scope before the scan

The change hotspots are witnesses/builtin.py and reporters/__init__.py. Both grew during implementation. Vocabulary comes from GLOSSARY.md and codebase-design: module, interface, depth, seam, adapter, leverage, locality. ADR 0001 (closed witness registry) and ADR 0004 (abstention is a result) are not re-litigated here.

Deletion test applied to each suspect: would removing it concentrate complexity, or just move it? Only a "yes, concentrates" earns a deepening candidate.

Candidate 1 Strong

Files: proveit/witnesses/builtin.py → new proveit/detectors.py

Problem
The diff.no_secrets Witness owns the detector catalog, Shannon entropy, per-line caps, finding shape and the verdict in one function. Its interface requires a full git Context. The complexity has no locality: nothing else can reach the detector, and tests need a repository fixture to exercise it.
Solution
One deep module with a small interface: scan_added_lines(lines) -> ScanResult(findings, lines_scanned). The Witness becomes a thin adapter. Patterns, entropy threshold, caps and finding shape move behind the seam.
Benefits
Higher depth and leverage: four direct unit tests replace a git fixture. The interface is the test surface. One adapter means a hypothetical seam; a second consumer would make it real. Deleting the module would scatter the detection complexity back into every Witness, so the deletion test confirms concentration.

Candidate 2 Worth exploring

Files: proveit/witnesses/builtin.py

Problem
One 600-line module holds diff, file, execution and API Witnesses. A reader bounces between unrelated concerns.
Solution considered
Split by claim family into three files.
Why it is not the recommendation
Deletion test says it just moves complexity. No interface shrinks, no depth increases, and the registry import changes add churn to a module whose behavior is already pinned by a fingerprint. Revisit only when a second consumer needs a separate seam.

Candidate 3 Speculative

Files: proveit/reporters/__init__.py

Problem
render(receipt, fmt) dispatches five formats from one module.
Solution considered
A reporter plugin registry so contributors add formats without touching core.
Why it is rejected
It creates a dynamic-loading seam inside code that writes public CI artifacts. That contradicts ADR 0001 and adds a code-loading surface to untrusted data. The current module is already deep: one interface hides five formats and the control-character cleaning boundary.

Top recommendation

Candidate 1. It is the only candidate that increases depth without opening a seam or moving code for its own sake.

Implemented as ADR 0002. The manager's hard constraint was that no function may change. We measured that constraint instead of asserting it: the pre-deepening implementation was reconstructed, the deterministic fingerprint ran, the new module was restored, and the fingerprint ran again. Both produced the same hash across 6 scenarios and 5 report formats. scripts/verify_all.py re-checks the hash on every release gate.
